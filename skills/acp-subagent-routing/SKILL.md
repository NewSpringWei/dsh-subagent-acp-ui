# ACP 子智能体路由

本部署通过配置页登记了若干 ACP 目标。每个启用的目标都会暴露一个委派工具，形如 `subagent_acp_<名称>`；运行时先看系统提示里的实际工具名，不要臆测。

## 管理目标

`acp_targets` 同时管理目标配置，不必让用户去插件页：

- `list` 查看目标。
- 检查连通性分两层：`test`（默认）只做 ACP 握手并返回模型列表，**不消耗模型 token**；`test` 传 `mode="verify"` 会真实发送一次短提示，**消耗少量 token**，用于确认端到端确实可用。日常排障先用默认探测，需要最终确认再用 verify。
- `add` / `update` / `remove` 增删改目标；保存后立即重建 provider 与委派工具，无需重启。
- 新增时至少提供 `name` 与 `command`。实例名决定 provider 与工具名，必须唯一。
- 模型传法因 CLI 而异：在 `args` 或 `env` 的值里写 `{model}` 占位符（例如 Qoder 用 `--model {model}`，OpenCode/MiMo 用对应的 `*_CONFIG_CONTENT` 环境变量）。不确定时先问用户，或让用户在配置页用预设与「浏览…」完成。
- 删除不可撤销，执行前向用户确认一次。
- 修改时实例名可以改，但那等于换一个目标（provider 名与工具名都会变）。

## 精确唤醒命令

每个启用的目标都有一个 `/acp-<名称> <任务>` 命令（例如 `/acp-qoder`）。它在用户已经明确要派给谁时使用：一条命令直接发起委派，跳过「先让模型决定要不要派、派给谁」那一轮。命令与工具调用走同一个官方 provider，行为一致，只是少了对话往返；模型仍按该目标的全局配置执行，不弹选择。

## 选择目标

1. 用户点名了某个具体 agent 就选对应目标。
2. 没点名时，用 `acp_targets` 的 `list` 查看可用目标与它们的启动命令，再按任务类型选：
   - 需要长上下文阅读、文档整理 → 该 agent 的强项模型；
   - 需要特定工具链（某家 CLI 自带的能力）；
   - 需要把任务丢到另一个额度来源。
3. 仍然拿不准就问用户，不要随便猜。

## 任务颗粒度

一次委派应当对应**一个能独立验收的交付物**，而不是一个模糊的方向。

- 好：「把 src/a.ts 和 src/b.ts 的错误处理统一成 Result 风格，改完回报文件路径与 diff 摘要，不要动测试。」
- 差：「帮我优化一下这个项目。」

拆分规则：

- 需要你先探索才能描述清楚的活，先在主会话探索，再把确定的子任务派出去。
- 一个委派写不满三句话，说明它太小：每次委派都要付进程启动 + ACP 握手的固定成本，自己顺手做完更快。
- 一个委派超过一屏还写不清，说明它太大：拆成两三个更小的委派，或留在主会话。
- 有依赖关系的多步任务不要一次性塞给子智能体，它不能追问、不能续跑。

## 委派方式

任务描述必须**自包含**：子智能体看不到本会话历史。一次写清这五项：

1. 工作目录（绝对路径）。
2. 目标与约束（允许改什么、禁止改什么）。
3. 验收标准（怎么算完成）。
4. 产物形式（文件路径 / 文本格式）。
5. 回报格式（改了哪些文件、跑了什么命令、结果如何）。

## 结果落地

- 需要文档或代码时，要求子智能体**直接写文件并回报路径**，不要把大段内容贴在回答里——既省 token，也方便按路径复核。
- 拿到回报后自己验证：文件是否存在、内容是否合理、命令输出是否可信。子智能体是另一个模型，可能编造改动。
- 涉及写操作时，要求它给出具体路径与命令；不要接受「已完成」这种结论式回复。

## 失败分析

委派失败时，工具结果里会出现一行官方诊断：

```
Subagent failure (provider: ACP; stage: <stage>; category: <category>; ...)
```

这是**事实**，不是结论。不要照着固定表格贴建议，按下面的步骤分析：

1. **定位阶段**：`stage` 说明卡在哪一步——`process`（进程起不来）、`initialize`（握手）、`new-session`（建会话）、`prompt`（执行中）、`teardown`（收尾）。
2. **读原始事实**：错误消息、`exit code`、`signal`。探测失败时还会附带该 CLI 的 stderr 尾部——多数 CLI 会自己写明原因（未登录、未知参数、命令不存在等）。
3. **复现一次**：用 `acp_targets` 的 test 重跑，确认错误稳定并拿到阶段。默认探测只做握手、**不消耗 token**；需要确认端到端真的可用时再加 `mode="verify"`，那次会**消耗少量 token**（配置页弹窗里的「测试」等价于 verify）。
4. **归因到最小可验证假设**，一次只验证一条：
   - 路径与可执行性：命令是否存在、能否执行、参数是否被该 CLI 接受
   - 认证：让用户在终端手动跑一次该 CLI，确认登录态
   - 参数：该 CLI 的 ACP 入口是子命令（`acp`）还是开关（`--acp`）
   - 版本与协议：该 CLI 的这个版本是否真的发布了 ACP 支持
5. **给用户一个动作**，而不是一串可能性。说清楚你先验证哪一条、怎么验证。

向用户报告失败时必须包含：**哪个目标、失败在哪一步、原始错误、你打算先验证什么**。不要只说「委派失败了」，也不要编造插件没提供过的建议。

## 不要做的事

- 不要对同一个失败的目标连续重试超过一次。
- 不要为了绕过失败去猜 ACP 启动参数。
- 不要把需要多轮交互或依赖对话上下文的任务交给 ACP 子智能体。
- 涉及删除、推送、发布的任务，未经用户明确确认不要委派。

## 限制（当前版本的真实约束）

- 不支持在调用时选择子智能体模型：模型在配置页按目标全局固定（该 CLI 的默认值或指定值）。
- 不支持委派深度上限、preset、结构化输出。
- 没有进程池：每次委派都要付一次进程启动与 ACP 握手成本。高频小任务不如自己做。
- 子智能体的权限请求由目标自身的 `permission` 策略（`allow` / `reject`）当场应答，不会上浮到主会话，也不会转交给主智能体审批。
